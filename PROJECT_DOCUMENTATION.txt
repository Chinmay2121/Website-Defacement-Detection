WEBSITE DEFACEMENT DETECTION SYSTEM - COMPREHENSIVE TECHNICAL DOCUMENTATION
================================================================================

OVERVIEW
========

This is an educational cybersecurity project that demonstrates how website 
defacement attacks occur and how to detect them in real-time using automated 
monitoring techniques. The system consists of three core components working 
together: a vulnerable web server, an intelligent detection monitor, and an 
attack simulator.

================================================================================
SYSTEM ARCHITECTURE
================================================================================

COMPONENT 1: VULNERABLE WEB SERVER (vulnerable_server.py)
----------------------------------------------------------

Purpose: A Flask-based web application intentionally designed with security 
vulnerabilities for educational demonstration.

Key Features:
- Multi-page website with homepage, about page, blog system with posts and 
  comments
- Admin panel accessible without authentication at /admin
- Dark theme interface with animated eye-tracking devil face emoji that 
  follows cursor movements
- Dynamic vulnerability showcase with auto-rotating slides demonstrating 5 
  common security flaws
- REST API endpoints for monitoring (/api/content, /api/images, /api/health)
- SQLite database storing blog posts and comments
- File upload functionality for logo management
- JSON-based content storage for website text and configuration

Intentional Vulnerabilities:
1. No Authentication: Admin panel requires no login credentials
2. XSS Vulnerable: Accepts raw HTML input without sanitization
3. No CSRF Protection: Forms lack anti-CSRF tokens
4. Unrestricted File Upload: No validation on uploaded images
5. SQL Injection Points: Database queries vulnerable to injection

How It Works:
- Runs on localhost:5000 using Flask development server
- Stores content in data/website_content.json with fields like homepage_title, 
  homepage_content, about_content, and logo_filename
- Logs all content changes to logs/change_log.json with timestamp, IP address, 
  and user agent
- Serves uploaded files from data/uploads/ directory
- Uses SHA-256 hashing to track image integrity via API endpoints

COMPONENT 2: ENHANCED DETECTION MONITOR (detection_monitor.py)
--------------------------------------------------------------

Purpose: Real-time monitoring system that detects unauthorized website 
modifications using multiple detection techniques.

Detection Methods:

1. File Integrity Monitoring (FIM):
   - Calculates SHA-256 hashes of critical files (website_content.json, 
     change_log.json)
   - Compares current hashes against baseline snapshots
   - Detects any byte-level modifications or file deletions
   - Triggers HIGH severity alert on file changes, CRITICAL on deletions

2. Content Monitoring with Pattern Detection:
   - Fetches live website content via /api/content endpoint
   - Compares current content against baseline using field-by-field analysis
   - Detects XSS patterns using 8 regex patterns: <script> tags, javascript: 
     protocol, event handlers (onerror, onload, onclick), dangerous functions 
     (alert(), eval()), and <iframe> tags
   - Identifies defacement keywords: hacked, pwned, owned, defaced, breach, 
     security, exploit, rooted, compromised, cracked, takeover, anonymous
   - Issues CRITICAL alerts for XSS detection, HIGH for suspicious keywords, 
     MEDIUM for benign content changes

3. Image Integrity Verification:
   - Retrieves image hashes from /api/images endpoint
   - Compares current image hashes against baseline
   - Detects image replacement, deletion, or addition
   - Alerts on HIGH severity for image modifications

Alert System:
- Four severity levels: CRITICAL (red, file deletion or XSS), HIGH (yellow, 
  file/image modified), MEDIUM (cyan, content changes), LOW (white, minor 
  issues)
- Dual logging: JSON format in defacement_alerts.json for machine parsing, 
  human-readable format in detection_log.txt
- Real-time console output with color-coded emojis and severity indicators
- Risk level tracking: Dynamically adjusts between LOW, MEDIUM, HIGH, CRITICAL 
  based on recent detections

Vulnerability Statistics Tracking:
- Maintains counters for: XSS attacks, file modifications, image changes, 
  content modifications, suspicious patterns
- Saves statistics to vulnerability_stats.json for dashboard consumption
- Tracks total checks performed and total detections across session

Monitoring Modes:
1. Create Baseline: Captures clean state of website (file hashes, content, 
   image hashes) and saves to baseline.json
2. Continuous Monitoring: Polls every 3 seconds (configurable), performs all 
   integrity checks, logs changes, updates status
3. One-time Check: Single verification without continuous loop
4. Dashboard Mode: Runs monitoring with web dashboard on port 5001

Web Dashboard (http://localhost:5001):
- Real-time threat level indicator with color-coded risk badge
- Statistics grid showing total checks, detections, detection rate, last 
  check time
- Vulnerability breakdown by category with counts
- Recent alerts feed showing severity, type, details, detected patterns
- Auto-refreshes every 3 seconds
- Visual pulse animations for CRITICAL alerts

COMPONENT 3: ATTACK SIMULATOR (attack_simulator.py)
----------------------------------------------------

Purpose: Simulates real-world website defacement attacks to test detection 
capabilities.

Attack Types:

1. Simple Defacement:
   - Changes homepage title to "HACKED BY ATTACKER"
   - Replaces content with red warning message
   - Highly visible, easy to detect

2. XSS Injection:
   - Injects <script>alert('XSS Vulnerability')</script> into content
   - Hidden within normal-looking text
   - Tests pattern-based XSS detection

3. Subtle Defacement:
   - Makes minor changes like altering contact email
   - Adds hidden HTML comments and invisible div elements
   - Includes tracking scripts disguised as comments
   - Harder to detect without automated monitoring

4. Redirect Injection:
   - Injects JavaScript setTimeout to redirect users after 3 seconds
   - Mimics phishing attack redirection techniques

5. Phishing Page:
   - Replaces homepage with fake security alert
   - Creates credential harvesting form
   - Simulates social engineering attack

6. Logo Replacement Attack (NEW):
   - Uploads malicious image to replace company logo
   - Can use custom image (baby-surprised.png) or creates red placeholder
   - Preserves all website content while only changing logo
   - Tests image integrity monitoring

7. Blog Comment XSS:
   - Injects XSS payloads via blog comment system
   - Tests multiple XSS vectors: script tags, image onerror handlers
   - Exploits user-generated content vulnerability

8. Combined Attack:
   - Simultaneously modifies content AND replaces logo
   - Creates comprehensive breach simulation
   - Tests multiple detection layers

9. Restore Original Content:
   - Resets website to clean state
   - Replaces logo with BMS.jpg from images directory
   - Restores default content across all pages
   - Clears change logs and resets database
   - Requires hard browser refresh (Ctrl+Shift+R)

Attack Execution Flow:
1. Check server availability via /api/health endpoint
2. Prepare malicious payload (content modifications and/or file uploads)
3. Send POST request to /admin/update endpoint
4. Log attack success/failure with color-coded console output
5. Server automatically logs changes to change_log.json

================================================================================
DATA FLOW
================================================================================

Normal Operation:
1. User views website → Server renders HTML from website_content.json and 
   database
2. Detection monitor polls every 3 seconds → Fetches content via API → 
   Compares to baseline
3. No changes detected → Logs "✓ No changes" to console

Attack Scenario:
1. Attacker runs simulator → Sends malicious payload to /admin/update
2. Server processes request → Updates website_content.json → Logs change to 
   change_log.json
3. Detection monitor's next check (within 3 seconds) → Calculates new hash
4. Hash mismatch detected → Runs pattern analysis on content
5. XSS patterns found → Triggers CRITICAL alert
6. Alert logged to JSON and text files → Console displays red warning
7. Dashboard updates risk level to CRITICAL → Vulnerability counter 
   incremented
8. Admin reviews logs and takes action

================================================================================
TECHNICAL IMPLEMENTATION DETAILS
================================================================================

Hashing Algorithm:
- SHA-256 chosen for cryptographic strength and collision resistance
- 64-character hexadecimal output provides 256-bit security
- Files read in 4096-byte chunks for memory efficiency
- Hash comparison is constant-time operation (O(1))

Pattern Detection Engine:
- Regex-based XSS detection using compiled patterns for performance
- Case-insensitive keyword matching for defacement terms
- Multi-pattern analysis returns all detected threats, not just first match
- Context preservation in alerts shows surrounding content for manual review

Monitoring Performance:
- 3-second polling interval balances detection speed vs server load
- Parallel checks of files, content, and images in single cycle
- Incremental hashing only recalculates changed files
- Async dashboard updates via auto-refresh without blocking monitoring

Security by Design:
- Baseline immutability: Stored baseline only updated on explicit user command
- Tamper detection: Monitor itself checks for baseline file modifications
- Comprehensive logging: All activities timestamped with ISO 8601 format
- Risk level decay: Automatically lowers threat level if no new detections 
  (every 10 checks)

================================================================================
LIMITATIONS & WARNINGS
================================================================================

Educational Constraints:
- No real security: Intentionally vulnerable, never use in production
- Local only: Designed for localhost testing, not internet-facing
- No encryption: All data stored in plaintext
- No authentication: Anyone with access can modify content
- No rate limiting: Vulnerable to DoS attacks

Detection Limitations:
- Polling-based: 3-second blind spot between checks
- Pattern-dependent: New XSS vectors may evade regex patterns
- No behavioral analysis: Cannot detect logic bombs or time-delayed attacks
- Client-side blind: Cannot detect DOM-based XSS executed in browser
- No network monitoring: Doesn't analyze HTTP traffic or SSL/TLS

================================================================================
SETUP & EXECUTION WORKFLOW
================================================================================

1. Installation: 
   Run setup.sh (Mac/Linux) to create virtual environment and install 
   dependencies (Flask, requests, watchdog, colorama, Pillow)

2. Start Server: 
   Terminal 1 → python src/vulnerable_server.py → Server runs on port 5000

3. Create Baseline: 
   Terminal 2 → python src/detection_monitor.py → Option 1 to snapshot clean 
   state

4. Start Monitoring: 
   Continue in Terminal 2 → Option 2 for continuous monitoring OR Option 3 
   for dashboard mode (port 5001)

5. Simulate Attacks: 
   Terminal 3 → python src/attack_simulator.py → Select attack type (1-11)

6. Observe Detection: 
   Monitor Terminal 2 shows real-time alerts, check dashboard at 
   http://localhost:5001

7. Review Logs: 
   Examine logs/defacement_alerts.json for detailed forensics

8. Restore System: 
   Run attack simulator → Option 9 to reset to clean state → Hard refresh 
   browser

contrasting with manual detection that could take hours or days. The 
pattern-based detection engine showcases how security tools identify malicious 
code, while the vulnerability showcase educates users about common web 
application weaknesses. The comprehensive logging and alerting system mirrors 
professional security monitoring tools used in enterprise environments.
